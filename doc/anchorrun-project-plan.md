# AnchorRun 项目计划

> 状态：当前主计划
> 更新日期：2026-09-22
> 当前阶段：0.x 产品边界与执行协议设计

## 1. 项目结论

AnchorRun 不应被定义成“让 Codex 从 WSL 操作远端机器的脚本”，而应被定义成：

> **AnchorRun 是一个本地源码权威、远端算力执行的声明式运行器。**
>
> 它把项目根目录中的配置转换成一次可复现、可审计的远端容器运行。源码留在本地，模型和数据留在远端，只有声明过的产物返回本地。

项目的核心边界不是透明地伪装“本地就是远端”，也不是双向同步整个工作区，而是显式描述并执行一次远端运行。

## 2. 项目名称与定位

0.x 阶段正式使用 `AnchorRun`：

- 项目名：`AnchorRun`
- 仓库名：`anchorrun`
- CLI：`anchorrun`
- 项目配置：`.anchorrun.yaml`
- 英文标语：`Source stays anchored. Compute runs remote.`
- 中文定位：本地源码权威的声明式远端运行器

名称中不使用 `WSL`。WSL 是当前主要的本地工作环境，但不是产品边界。核心设计也应适用于普通 Linux，并为未来支持 macOS 保留空间。

命令、Python 包和配置标识统一使用小写 `anchorrun`。在 1.0 公开发布前重新检查 GitHub、PyPI、域名和商标占用；只有出现阻断性冲突时才再次考虑改名。

## 3. 四个权威来源

AnchorRun 必须明确区分四类事实的权威位置：

| 对象 | 权威位置 | 说明 |
| --- | --- | --- |
| 源码 | 本地项目目录 | 所有源码编辑只在本地完成 |
| 运行环境 | 远端容器镜像 | 镜像必须使用 digest 锁定 |
| 模型与数据 | 远端持久目录 | 不随源码同步，默认只读挂载 |
| 一次运行的事实 | Run Manifest | 记录源码、命令、镜像、目标、状态和产物 |

核心原则：

> **本地源码是锚点，远端执行是一次显式运行。**

## 4. 总体架构

```text
本地项目目录 + .anchorrun.yaml
                 │
                 ▼
        配置解析、校验与运行规划
                 │
                 ├── 生成 run-id 与源码指纹
                 │
                 ├── 单向推送源码快照 ───────────────┐
                 │                                  ▼
                 │                    <remote_root>/runs/<run-id>/src
                 │                                  │
                 │                         digest 锁定的容器
                 │                         ├── /workspace  本次源码
                 │                         ├── /models     只读
                 │                         ├── /data       只读
                 │                         ├── /cache      可写持久缓存
                 │                         └── /outputs    本次运行输出
                 │
                 └── Run Manifest + 声明产物 ◀────────────┘
```

推荐的远端目录结构：

```text
<remote_root>/
├── assets/
│   ├── models/
│   └── datasets/
├── cache/
└── runs/
    └── <run-id>/
        ├── src/
        ├── outputs/
        ├── logs/
        └── run.json
```

## 5. 项目职责

### 5.1 核心职责

AnchorRun 负责：

1. 从当前目录向上发现项目配置。
2. 解析并严格校验目标机器、目录、镜像、设备、挂载和产物配置。
3. 将配置和命令解析为可预览的执行计划。
4. 生成 `run-id`、源码指纹和本次运行的远端目录。
5. 将本地源码单向同步成远端运行快照。
6. 在锁定镜像、固定工作目录和明确挂载中执行命令。
7. 管理运行状态、退出码、日志和 Run Manifest。
8. 区分模型、数据、缓存和输出的挂载语义。
9. 只允许拉回配置中声明的、本次运行产生的产物。
10. 提供 `doctor`、安全检查、超时、中断和失败诊断。
11. 为 Codex、Claude Code 等 Agent 提供薄适配层。

### 5.2 明确不负责

以下内容不属于 1.0 范围：

- 双向实时文件同步。
- 在远端编辑源码并同步回本地。
- 模拟 VS Code Remote SSH 或完整远端 IDE。
- 创建云主机、申请 GPU 或配置物理机器。
- 多用户队列、资源调度或集群管理。
- 上传、下载和版本管理模型或数据集。
- 保存 SSH 私钥、Registry 密码或其他秘密。
- 在远端安装和运行 Codex 本体。
- Kubernetes、多节点训练和分布式作业编排。
- 远端常驻守护进程或控制平面。

## 6. 三层产品结构

```text
项目配置
  描述每个项目的本地源码、目标机器、镜像、挂载和产物事实
        │
        ▼
核心 CLI
  实现校验、规划、同步、执行、状态记录和安全边界
        │
        ▼
Agent Skill
  告诉 Agent 何时以及如何调用 CLI，不重新实现执行逻辑
```

核心能力必须属于 CLI。Skill 只是适配器和使用策略，不能成为唯一实现。

## 7. 当前实现基础

当前 0.1 实现已经具备以下基础能力：

- `.anchorrun.yaml` 的向上发现和严格字段校验。
- SSH 目标只接受用户 SSH 配置中的简单别名。
- 远端目录的绝对路径、路径穿越和根目录保护。
- 容器镜像必须使用 `sha256` digest 锁定。
- WSL 到远端的单向 `rsync`。
- 远端删除需要配置和命令行两个独立开关。
- Docker 和 Podman 运行时抽象。
- GPU 设备、安全选项、附加挂载和环境变量传递。
- `doctor`、`prepare`、`show`、`sync`、`exec`、`shell`、`pull` 命令。
- 只允许拉回配置声明的产物目录。
- Codex Skill 保持为薄适配层。
- 当前 37 个单元测试通过，覆盖配置安全、命令生成、远端编排与 CLI 分发。

这些基础应当保留，不需要重写 SSH、rsync 和容器执行层。

## 8. 当前核心缺口

### 8.1 没有运行级源码快照

源码目前直接同步到长期可变的 `remote_root`，然后直接挂载到容器。这种模式无法隔离并发运行，也不能证明某个结果对应哪一份源码。

### 8.2 `state_dir` 尚未形成运行账本

配置已经声明 `state_dir`，但它目前只被解析和展示，没有用于保存运行状态、manifest、日志索引或最近运行信息。

### 8.3 产物没有绑定本次运行

`pull` 当前从固定远端目录拉回文件。若目录中存在旧结果，用户无法判断文件是否由本次命令产生。

### 8.4 挂载缺少领域语义

当前 `mounts` 只是任意路径映射，没有区分：

- 模型：持久、只读。
- 数据集：持久、只读。
- 缓存：持久、可写。
- 输出：本次运行专属、可拉回。

### 8.5 缺少运行生命周期

目前没有统一的：

- `run-id`
- 源码指纹
- Run Manifest
- `planned/running/succeeded/failed/interrupted/unknown` 状态
- 中断和 SSH 断开处理
- 并发隔离
- 远端保留与清理策略

## 9. 方案比较

### 方案 A：继续增强同步器

保留 `sync → docker run → pull`，只增加日志、命令模板和更多检查。

- 工作量较小。
- 可以较快满足个人日常使用。
- 无法可靠证明结果与源码、镜像和运行之间的对应关系。
- 长期会停留在“安全的个人远程执行脚本”。

### 方案 B：升级为运行协议，推荐

保留现有 SSH、rsync 和容器实现，在其上增加：

- `run-id`
- 源码指纹与运行快照
- Run Manifest
- 运行级输出目录
- 模型、数据、缓存和输出语义
- 状态、中断、保留和清理规则

该方案最符合“本地源码权威 + 声明式远端容器执行”的目标，同时保持系统足够轻量。

### 方案 C：直接构建远程计算平台

增加守护进程、Web UI、队列、机器注册、资源发现、多用户权限和集群调度。

- 能力范围最大。
- 会直接进入 DevPod、Slurm 和云平台的竞争范围。
- 复杂度和运维成本远超当前真实需求。
- 会削弱项目最清晰的产品边界。

1.0 不采用该方案。

## 10. 实施路线

### P0：冻结产品契约

目标：在继续修改代码前，明确稳定边界。

交付内容：

- 本文档作为主项目计划。
- 补充独立的配置参考和远端目录规范。
- 明确现有命令的兼容承诺。
- 明确 schema v1 的扩展策略。
- 定义 `plan`、`exec`、`pull` 与未来 `run` 的关系。

完成标准：

- 文档能明确回答项目做什么、不做什么。
- 任意运行在执行前都能生成一个不产生副作用的完整计划。

### P1：引入运行身份和运行账本

目标：让每次远端执行成为可追溯的独立运行。

交付内容：

- 为每次执行生成唯一 `run-id`。
- 计算源码指纹；Git 项目至少包含 HEAD 与脏工作区摘要。
- 在 `state_dir/runs/<run-id>/` 写入本地 manifest。
- 在远端创建 `runs/<run-id>/src` 和 `runs/<run-id>/outputs`。
- 容器挂载本次运行的源码目录，而不是长期共享源码根目录。
- 记录目标、镜像、命令、开始时间、结束时间和退出状态。

完成标准：

- 任一结果都能追溯到具体源码、镜像、目标和命令。
- 两次并发运行不共享源码目录或输出目录。

### P2：引入远端资产语义

目标：正式支持“WSL 保存源码，远端保存模型和数据”。

交付内容：

- 为模型、数据集、缓存和输出定义独立配置结构。
- 模型和数据集默认只读。
- 缓存允许持久可写，但不得混入源码或产物。
- 输出自动绑定到本次 `run-id`。
- `pull` 默认只拉取指定运行的声明产物。

完成标准：

- 模型和数据不会被普通运行意外修改。
- 不会把上一次运行遗留的文件误认为本次结果。

### P3：补齐可靠性

目标：使工具可以安全处理真实的长时间 GPU 和编译任务。

交付内容：

- Ctrl-C 和本地信号传递。
- SSH 断开后的状态判定。
- 可配置超时。
- 运行级并发隔离。
- 远端磁盘空间检查。
- 失败同步和部分产物的处理规则。
- 运行保留数量或保留天数。
- 显式、安全的远端清理命令。

完成标准：

- 中断或网络异常后不会把运行错误标记为成功。
- 不会静默遗留无法识别的运行状态。
- 清理操作有明确目标和防误删保护。

### P4：测试、分发与公开使用

目标：从个人工具升级为其他开发者能够安装和信任的项目。

交付内容：

- 建立正式 Git 仓库和版本策略。
- GitHub Actions 测试与构建流程。
- PyPI 或等价 Python 包分发。
- `uv tool install` 和 `pipx` 安装路径。
- 最小 SSH/Linux 示例。
- AMD GPU、NVIDIA GPU 和普通 CPU 示例。
- 从当前 0.1 配置迁移的说明。
- 本地到伪远端执行链的集成测试。

完成标准：

- 新用户可在十分钟内完成安装、配置检查和第一次远端运行。
- 发布包能够在干净环境中安装和运行。

### P5：Agent 生态适配

目标：让不同 Agent 使用同一套执行契约。

交付内容：

- Codex Skill。
- Claude Code Skill 或命令说明。
- 通用 `AGENTS.md` 集成示例。
- 结构化 JSON 输出，方便 Agent 解析状态和产物。

完成标准：

- Agent 适配层不包含 SSH、rsync 或容器实现。
- 删除 Skill 后，CLI 仍能被人类完整使用。

## 11. 建议的命令演进

保留当前命令，并渐进增加运行语义：

```text
anchorrun doctor
anchorrun prepare
anchorrun show
anchorrun plan -- <command...>
anchorrun sync
anchorrun exec -- <command...>
anchorrun runs list
anchorrun runs show <run-id>
anchorrun pull <run-id>
anchorrun clean --run <run-id>
```

短期内不引入大量命名任务或工作流 DSL。`exec -- <command...>` 仍然是主要入口。只有当多个真实项目反复出现同一命令配置需求时，再增加可选的 `tasks:` 配置。

## 12. 配置演进原则

1. 优先为 schema v1 增加可选字段。
2. 只有出现无法兼容表达的变化时才升级 schema v2。
3. 项目配置中不存储凭证。
4. SSH 认证继续由用户的 SSH 配置负责。
5. 路径、镜像和设备必须在真正执行前完成校验。
6. 所有默认行为应当偏向只读、单向和不删除。
7. 配置解析结果必须能够通过 `show` 或 `plan` 完整展示。

## 13. 测试策略

### 单元测试

覆盖：

- 所有配置字段的正确与错误输入。
- 路径逃逸、根目录、空值和未知字段。
- 镜像 digest、SSH 别名和环境变量验证。
- rsync、SSH 和容器命令的参数生成。
- 删除和清理操作的双重确认规则。
- 每个运行状态转换。
- manifest 序列化和反序列化。

### 集成测试

覆盖：

- 本地临时目录到伪远端目录的同步。
- 一次完整的 `plan → sync → exec → manifest → pull`。
- 容器命令失败。
- rsync 失败。
- SSH 超时和断开。
- Ctrl-C 中断。
- 两个并发运行。
- 旧产物不会被当成本次运行产物。

### 发布验证

覆盖：

- 从构建包安装，而不是只通过源码目录运行。
- `anchorrun --help` 和所有子命令 smoke test。
- 示例配置能够通过 `doctor` 的本地校验。
- Skill 使用系统校验工具验证。

## 14. 主要失败模式

| 失败模式 | 必须采取的行为 |
| --- | --- |
| 本地源码同步中断 | 不启动容器，将运行标记为同步失败 |
| SSH 在运行中断开 | 不推断远端进程已停止，状态记为 `unknown` 或重新探测 |
| 容器命令返回非零 | 保留日志和 manifest，状态记为 `failed` |
| 产物目录不存在 | 明确报告缺失，不创建伪成功结果 |
| 模型或数据目录不可读 | 在容器启动前失败 |
| 远端空间不足 | 在同步前失败并给出目标路径 |
| 两次运行同时启动 | 分配不同 run 目录，不覆盖彼此 |
| 用户请求远端删除 | 必须使用显式、精确的 run-id 或经过双重确认的目标 |

## 15. 1.0 验收标准

达到以下条件后，项目才适合标记为 1.0：

- 一个新项目只需要根目录配置文件，不需要项目专属脚本。
- `doctor` 能提前发现 SSH、镜像、设备、目录和挂载错误。
- 每次运行都有唯一 `run-id` 和完整 Run Manifest。
- Manifest 能回答源码、机器、镜像、命令和远端资产版本。
- 本地源码永远不会被普通远端操作反向覆盖。
- 模型和数据默认只读。
- 只有本次运行的声明产物可以拉回。
- 并发运行不会互相污染源码和输出。
- 中断和网络断开后存在明确状态。
- 配置、安全边界和命令规划分支具有完整测试。
- CLI 可以独立使用，Skill 不是运行时依赖。
- 新用户可在十分钟内完成首次远端运行。

## 16. 下一步执行顺序

接下来的工作按以下顺序进行：

1. 以本文档冻结产品定义和职责边界。
2. 设计 Run Manifest 和运行状态机。
3. 设计兼容现有配置的远端 `runs/<run-id>` 布局。
4. 实现只读的 `plan` 命令。
5. 让现有 `exec` 生成 run-id、快照和 manifest。
6. 将 `pull` 绑定到明确的 run-id。
7. 增加模型、数据、缓存和输出语义。
8. 补齐中断、并发、清理和集成测试。
9. 最后再处理公开分发和多 Agent 适配。

在 P1 完成前，不继续扩张远程调度、Web UI 或多主机控制等范围。
